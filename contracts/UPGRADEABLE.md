# 可升级合约架构说明

## 架构对比

### 传统部署（当前）
```
┌─────────────────────────────────────┐
│      Pool Contract                  │
│  ┌─────────────────────────────┐   │
│  │  逻辑代码 + 状态变量         │   │
│  └─────────────────────────────┘   │
│  地址: 0xB6f...                  │
└─────────────────────────────────────┘
       ❌ 一旦部署无法修改
```

### 可升级部署（推荐）
```
┌─────────────────────────────────────┐
│     ERC1967 Proxy                   │
│  ┌─────────────────────────────┐   │
│  │  delegatecall 到逻辑合约    │   │
│  └─────────────────────────────┘   │
│  地址: 0xB6f... (保持不变)        │
└─────────────────────────────────────┘
              │ delegatecall
              ▼
┌─────────────────────────────────────┐
│   PoolUpgradeable (V1)              │
│  ┌─────────────────────────────┐   │
│  │  逻辑代码                    │   │
│  └─────────────────────────────┘   │
│  地址: 0x1234... (可替换)        │
└─────────────────────────────────────┘
              │ 升级
              ▼
┌─────────────────────────────────────┐
│   PoolUpgradeable (V2)              │
│  ┌─────────────────────────────┐   │
│  │  新逻辑代码                  │   │
│  └─────────────────────────────┘   │
│  地址: 0x5678...                   │
└─────────────────────────────────────┘
              ✅ Proxy 地址不变
              ✅ 所有状态数据保留
```

## 核心概念

### 1. 代理模式
- **Proxy 合约**: 存储所有状态变量，通过 `delegatecall` 调用逻辑合约
- **逻辑合约**: 只包含代码，不存储状态
- **地址分离**: Proxy 地址永远不变，逻辑合约地址可以更新

### 2. UUPS (Universal Upgradeable Proxy Standard)
- 更安全：升级权限在逻辑合约中控制
- 更节省 gas：相比 Transparent Proxy
- OpenZeppelin 推荐

## 部署流程

### 初始部署
```bash
# 部署可升级合约
forge script script/DeployUpgradeablePool.s.sol:DeployUpgradeablePool \
  --rpc-url https://sepolia.drpc.org \
  --broadcast \
  --verify
```

### 升级合约
```bash
# 升级到新版本
forge script script/UpgradePool.s.sol:UpgradePool \
  --rpc-url https://sepolia.drpc.org \
  --broadcast
```

## 关键限制

### ❌ 不能修改的部分
1. **状态变量布局**：不能删除或重新排序现有变量
2. **现有函数签名**：不能修改现有函数的参数或返回值

### ✅ 可以添加的部分
1. **新的状态变量**：添加到末尾
2. **新的函数**：任何新功能
3. **修改函数逻辑**：内部实现可以更改

## 代码示例

### 正确的升级
```solidity
// V1
contract PoolV1 {
    uint256 public value1;
    function setValue1(uint256 v) external { value1 = v; }
}

// V2 - 正确
contract PoolV2 {
    uint256 public value1;      // ✅ 保留原有变量
    uint256 public value2;      // ✅ 新变量添加到末尾
    function setValue1(uint256 v) external { value1 = v * 2; } // ✅ 逻辑可改
    function setValue2(uint256 v) external { value2 = v; }     // ✅ 新函数
}
```

### 错误的升级
```solidity
// V2 - 错误
contract PoolV2 {
    uint256 public value2;      // ❌ 重新排序变量
    uint256 public value1;
}
```

## 迁移方案

### 选项 A: 继续使用当前合约
- 优点：已有测试数据，无需迁移
- 缺点：无法升级逻辑

### 选项 B: 部署新的可升级合约
- 优点：支持未来升级
- 缺点：需要重新配置价格源

### 选项 C: 保持当前合约 + 新功能用可升级
- 新功能使用可升级合约
- 核心合约保持不变

## 安全注意事项

1. **升级前测试**: 在测试网充分测试新版本
2. **时间锁**: 考虑添加升级时间锁
3. **多签控制**: 升级权限使用多签钱包
4. **紧急暂停**: 添加 pause 功能
